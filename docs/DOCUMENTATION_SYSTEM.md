# Регламент системы документации

[← К оглавлению](index.md)

## 1. Назначение

Система превращает документацию в постоянную общую память людей и агентов. Она
предназначена для любых проектов, прежде всего программных, исследовательских и
связанных с данными.

Основные цели:

- не терять решения и выводы в истории чатов;
- не исследовать повторно уже изученные части проекта;
- поддерживать параллельную работу нескольких чатов;
- сохранять происхождение каждого важного вывода;
- обеспечивать актуальное состояние документации в любой момент времени;
- позволять начинать чтение с `index.md` и двигаться по дереву ссылок.

## 2. Три слоя знаний

### 2.1. Первичные материалы

Код, данные, исходные документы, требования пользователя, результаты тестов и
экспериментов. Они являются доказательствами. Каталог значимых материалов
поддерживается в [источниках](sources/index.md).

### 2.2. Поддерживаемая база знаний

Все страницы в `docs/`. Агент создаёт, связывает, обновляет и проверяет их.

### 2.3. Правила обслуживания

Корневой `AGENTS.md`, этот регламент, шаблоны и `scripts/docs_ctl.py`. Корневой
файл содержит только обязательные краткие правила, а подробности находятся здесь.

## 3. Карта файлов

| Путь | Назначение | Источник истины |
|---|---|---|
| `docs/index.md` | Корень дерева ссылок | Для навигации |
| `docs/MAIN_DESCRIPTION.md` | Стабильная цель и границы проекта | Для назначения проекта |
| `docs/CURRENT_STATE.md` | Краткая автоматически собираемая карта | Нет, это представление |
| `docs/TASKS_DASHBOARD.md` | Статусы и связи всех задач | Нет, это представление |
| `docs/tasks/` | Требования, история и выводы отдельных задач | Для истории работы |
| `docs/knowledge/` | Актуальные тематические знания | Для текущего знания |
| `docs/decisions/` | Межзадачные решения и их основания | Для принятых решений |
| `docs/sources/` | Карточки и каталог первичных материалов | Для происхождения сведений |
| `docs/templates/` | Единые шаблоны страниц | Для формы документов |

## 4. Когда создавать задачу

Создавайте задачу, если появился новый самостоятельный результат, которого можно
достичь, проверить и завершить отдельно.

Задача обязательна для:

- новой возможности или крупного изменения;
- самостоятельного исправления сложной ошибки;
- исследования структуры проекта;
- исследования архитектуры, зависимостей или потоков данных;
- исследования датасета, его формата, статистик и качества;
- диагностики, даже если исправление пока не разрешено;
- сравнения технологий или подходов;
- эксперимента или проверки гипотезы;
- создания самой документации и её крупной перестройки.

Не создавайте отдельную задачу для:

- небольшого уточнения уже активной цели;
- локального рефакторинга, необходимого для текущей задачи;
- повторного запуска проверки;
- исправления опечатки в рамках текущей задачи.

Новый чат на первом содержательном запросе создаёт новую задачу, кроме явного
продолжения существующей. Новая независимая цель внутри чата также создаёт новую
задачу. Для идеи, которую пока не начали выполнять, разрешено создать задачу со
статусом `planned`.

## 5. Жизненный цикл задачи

Допустимые служебные статусы:

| Значение | Смысл |
|---|---|
| `planned` | Запланирована, работа не начата |
| `active` | Выполняется |
| `waiting` | Ожидает ответа или внешнего события |
| `blocked` | Есть явно описанная преграда |
| `done` | Критерии завершения выполнены |
| `cancelled` | Отменена с указанием причины |
| `superseded` | Заменена другой задачей |

Создание:

```text
python scripts/docs_ctl.py create "Название задачи"
```

Команда безопасно резервирует номер, создаёт папку и три обязательных файла,
затем обновляет общие страницы.

### 5.1. Описание

`*_descr.md` содержит цель, границы, критерии завершения, требования пользователя,
зависимости, план, допущения, рассмотренные варианты и краткие обоснования.
Каждое существенное уточнение пользователя заносится сюда в том же сеансе.

Не сохраняйте скрытое пошаговое рассуждение модели. Сохраняйте выводы, варианты,
причины выбора и проверяемые допущения.

### 5.2. Журнал

`*_logs.md` хранит значимые события в хронологическом порядке. Тело журнала
дописывается, старые записи не переписываются. Изменять разрешено оглавление
важных записей в начале.

Формат заголовка:

```text
## L-YYYYMMDD-NN — Тип: краткое описание
```

Запись содержит результат, основания, затронутые файлы и следующий шаг. Полные
сырые выводы команд при необходимости сохраняются отдельными файлами и
связываются ссылкой.

### 5.3. Выводы

`*_concl.md` всегда отражает текущие выводы задачи, в том числе промежуточные.
Обязательные разделы:

- краткий итог;
- подтверждённые результаты и доказательства;
- полезные наблюдения;
- проблемы и преграды;
- как проблемы решались;
- открытые вопросы;
- влияние на глобальное состояние;
- созданные и изменённые материалы.

## 6. Исследования и глобальные знания

Исследование никогда не считается «просто чтением». Оно создаёт задачу и
оставляет долговременный результат.

После исследования агент обязан:

1. Зафиксировать метод, область просмотра и все полезные выводы в `*_concl.md`.
2. Приложить ссылки на код, данные, команды, тесты или источники.
3. Создать или обновить одну либо несколько страниц в `docs/knowledge/`.
4. В глобальной странице оставить ссылки на задачи-основания.
5. Выполнить синхронизацию, чтобы `CURRENT_STATE.md` и оглавление знаний получили
   актуальные ссылки.

Типичные глобальные страницы создаются по мере необходимости:

- `PROJECT_STRUCTURE.md` — каталоги, модули и точки входа;
- `ARCHITECTURE.md` — компоненты, границы и потоки;
- `DATASETS.md` — наборы данных, схемы, качество и ограничения;
- `DEVELOPMENT.md` — запуск, тестирование и окружение;
- `EXTERNAL_INTERFACES.md` — внешние службы и форматы взаимодействия;
- отдельные предметные страницы.

Не создавайте пустые страницы «на будущее». Одна страница должна иметь одну
устойчивую тему. При росте страницы разделяйте её и обновляйте ссылки.

Глобальная страница описывает текущую истину, а не хронологию. При изменении
знания обновите основной текст, укажите прежнее утверждение как устаревшее, если
оно повлияло на решения, и свяжите обновление с новой задачей.

## 7. Уровни достоверности

Для важных утверждений используйте явные пометки:

- **Подтверждено** — есть проверяемое доказательство.
- **Гипотеза** — правдоподобно, но требует проверки.
- **Предложение** — возможное будущее действие.
- **Решение** — вариант принят уполномоченным участником.
- **Устарело** — заменено новым знанием со ссылкой на замену.

Нельзя превращать предположение агента в подтверждённый факт без основания.

## 8. Решения

Решение выносится в `docs/decisions/`, если влияет на несколько задач,
архитектуру, совместимость, формат данных, безопасность или долгосрочные расходы.

Запись решения содержит контекст, варианты, принятое решение, основания,
последствия, доказательства и связанные задачи. Неудачное решение не удаляется:
оно получает статус `superseded` и ссылку на замену.

## 9. Актуальность

Документация обновляется не «в конце когда-нибудь», а одновременно с изменением
знания или проекта.

Обязательные контрольные точки:

- после уточнения требований;
- после значимого исследования;
- после принятия решения;
- после эксперимента или проверки;
- после изменения поведения кода, схемы данных или интерфейса;
- после обнаружения либо решения проблемы;
- перед завершением задачи;
- перед итоговым ответом о выполненной работе.

После изменения запустите `python scripts/docs_ctl.py sync`. Перед итогом —
`python scripts/docs_ctl.py check`.

Если страница не может быть немедленно актуализирована, нельзя молча оставлять
старое содержание. Пометьте его как непроверенное, опишите причину и создайте
задачу на актуализацию.

## 10. Связность

Используйте обычные относительные Markdown-ссылки. Каждая страница должна:

- быть достижима из [главного оглавления](index.md);
- иметь обратную ссылку на оглавление своего раздела;
- ссылаться на связанные задачи, решения, знания и источники;
- не дублировать подробности, уже имеющие основную страницу.

Направление ссылок:

```text
index → раздел → тематическая страница → задача/доказательство
задача → выводы → глобальная страница знания
CURRENT_STATE → глобальная страница знания → задачи-основания
```

## 11. Параллельная работа

Каждый чат владеет одной активной папкой задачи. Это основная граница записи.
Другие задачи читаются для контекста, но не переписываются без явной причины.

Центральные страницы содержат автоматически собираемые блоки. Программа
`docs_ctl.py` использует файл блокировки, повторно читает источники и строит
представления заново. При конфликте приоритет имеют файлы задач и тематические
страницы, а не дашборд.

Субагенты не нужны для согласования чатов. При их явном использовании основной
агент назначает непересекающиеся файлы и остаётся единственным редактором общих
страниц.

Если проект ведётся в отдельных рабочих деревьях Git, изменения станут общими
только после объединения веток. Перед объединением повторно выполните
синхронизацию и проверку.

## 12. Безопасность и объём

- Не сохраняйте секреты и содержимое файлов окружения.
- Не вставляйте большие двоичные файлы в документацию; создавайте карточку
  источника и ссылку.
- Не копируйте полные журналы команд, если достаточно результата и ссылки.
- Не храните одно и то же описание одновременно в `AGENTS.md`,
  `MAIN_DESCRIPTION.md` и задаче.
- Разделяйте слишком большие страницы по темам и поддерживайте оглавления.

## 13. Проверка здоровья

Команда `python scripts/docs_ctl.py check` синхронизирует представления и
проверяет:

- наличие обязательных глобальных файлов;
- структуру и служебные поля задач;
- уникальность номеров задач;
- допустимость статусов;
- существование локальных ссылок;
- достижимость страниц из `docs/index.md`;
- корректность связей между задачами;
- отсутствие зависших файлов блокировки.

Проверка программы не заменяет смысловой просмотр. При крупном изменении агент
дополнительно ищет противоречия, дублирование, устаревшие выводы и темы без
отдельной страницы.

## 14. Критерии завершения задачи

Задача может получить статус `done`, только если:

1. Выполнены критерии из описания.
2. Результаты проверены.
3. Описание, журнал и выводы актуальны.
4. Все полезные наблюдения сохранены в выводах.
5. Многократно полезные знания перенесены в `docs/knowledge/`.
6. Межзадачные решения перенесены в `docs/decisions/`.
7. Проблемы, способы решения и открытые вопросы явно описаны.
8. Общие страницы синхронизированы.
9. Автоматическая проверка завершилась без ошибок.

## 15. Изменение самой системы

Изменение структуры документации является отдельной задачей. Сначала обновите
регламент и шаблоны, затем программу, затем существующие страницы. Зафиксируйте
совместимость и миграцию в выводах задачи и при необходимости в отдельном
решении.

## 16. Перенос основы в новый проект

Рабочая документация неизбежно содержит предметные задачи и знания текущего
проекта, поэтому её нельзя целиком копировать в другой проект после начала работ.
Для экспорта первоначальной универсальной основы используйте:

```text
python scripts/docs_ctl.py export-template <новый_каталог>
```

Каталог назначения не должен существовать. По умолчанию команда переносит
`AGENTS.md`, пустые глобальные страницы, регламент, шаблоны и служебную программу,
но не переносит задачи, журналы, выводы, решения, источники и знания текущего
проекта. Первая задача нового проекта получает номер `TASK_001`.

После копирования команда автоматически синхронизирует и проверяет новую основу.
