# Дизайн оценки верификатора L2

[← К глобальным знаниям](index.md)

## Кратко

Верификатор L2 проверяется на соответствующих парах `orig` и `fail_pic`: при
прочих равных итоговый балл достоверности исходной картинки должен быть выше,
чем у её контролируемо испорченной версии. Фронтирные генераторы и фронтирные
модели-судьи выполняют разные роли и должны находиться в разных экспериментах.

## Подтверждённые сведения

- **Подтверждено по требованиям проекта:** вход генератора — текстовый блок и
  подпись; вход судьи для оценки достоверности — те же текстовые сведения и
  проверяемая картинка.
- **Подтверждено по задаче `TASK_001`:** в основном тесте `orig` не передаётся
  судье как эталон. Иначе судья может находить визуальные отличия вместо
  смысловых нарушений.
- **Предложение:** минимальная матрица сравнения состоит из двух моделей-судей
  и двух промптов: общего и специализированного по сущностям. Она отделяет
  вклад промпта от вклада модели.
- **Уточнено:** внешняя сильная модель-судья с общим промптом — обязательная
  базовая линия; она представляет прямое решение без протокола сущностей.

## Четыре оси и общий балл

По каждой оси судья возвращает только `1`, `3` или `5`:

| Ось | Смысл |
|---|---|
| Faithfulness (`F`) | Достоверность: соответствие тексту, отсутствие визуальных галлюцинаций и пропусков критических компонентов |
| Clarity (`Cl`) | Ясность: читаемость и понятность структуры |
| Compactness (`Co`) | Компактность: отсутствие лишнего, перегруза и визуального шума |
| Style (`S`) | Стиль: соответствие академическому визуальному стилю |

Общий балл вычисляет фреймворк, а не модель:

`Overall = 0.45 × F + 0.25 × Cl + 0.15 × Co + 0.15 × S`.

Веса являются настраиваемыми параметрами эксперимента, но указанные значения —
начальные значения по умолчанию.

## Достоверность через сущности

1. Судья выделяет минимум три критические сущности или отношения из
   `text_block` и `caption`. Сущность содержит цитируемый фрагмент входного
   текста; недостающие до трёх сущности добираются разбиением составных
   требований на атомарные элементы.
2. Судья перечисляет визуальные сущности: блоки, стрелки, подписи, модули,
   значения, направления и другие проверяемые элементы.
3. Сущности сопоставляются со статусами: `supported` — поддерживается;
   `unsupported` — есть на картинке, но не подтверждается текстом;
   `missing` — требуется текстом, но отсутствует на картинке.
4. `P` — число поддержанных текстовых сущностей, `U` — число неподдержанных
   визуальных сущностей, `M` — число отсутствующих текстовых сущностей.
   `Coverage = P / (P + M)`.

Начальное детерминированное правило `F`, которое фреймворк перепроверяет по
счётчикам:

- если текстовых сущностей меньше трёх — ответ невалиден и требует повтора;
- если `U ≥ 2`, то `F = 1`;
- если `U = 1` и `M ≥ 1`, то `F = 1`;
- если `U = 1` и `M = 0`, то `F = 3`;
- если `U = 0` и `Coverage ≥ 0.80`, то `F = 5`;
- если `U = 0` и `0.60 ≤ Coverage < 0.80`, то `F = 3`;
- иначе `F = 1`.

Границы включаются в верхнюю категорию (`≥`). Пороги `0.60` и `0.80` должны
храниться в конфигурации запуска, чтобы последующие исследования могли менять
их без изменения кода.

## Два разных протокола

### Слепой диагностический тест L2

Текущий фреймворк для контролируемых пар выполняет два полностью независимых
вызова с одним шаблоном и одной моделью:

1. `orig_pic + caption + text_block`;
2. `fail_pic + caption + text_block`.

Каждый вызов видит ровно одну картинку. Главная парная проверка —
`F(orig) > F(fail)`, дополнительно сравниваются остальные оси и общий балл.

### Сравнение генераторов

Участники: Human — рисунок из статьи; Our Pipeline — полный автономный процесс;
Frontier — сильные внешние генераторы. Все генераторы получают одинаковые
`text_block` и `caption`. Для каждого участника сохраняются оценки по осям и
общий балл; Our Pipeline попарно сравнивается с Human и каждым Frontier.

Требование одновременно передавать судье эталон и сгенерированную картинку
относится к отдельному режиму с эталоном. Его нельзя смешивать со слепым тестом:
иначе судья может искать визуальные различия вместо смыслового соответствия.
Результаты двух режимов должны храниться и публиковаться раздельно.

## Агрегация

- Точечная оценка: средние `F`, `Cl`, `Co`, `S` и `Overall` отдельно для
  каждого участника.
- Парная оценка: по каждой оси `win`, `tie`, `lose` и соответствующие проценты
  Our Pipeline против каждого оппонента. Для диагностического набора роли пары
  — `orig` против `fail`.
- Сырой ответ VLM не является окончательной метрикой: фреймворк проверяет
  допустимые значения, пересчитывает `F`, `Coverage` и `Overall`, а расхождения
  сохраняет в аудите.

## Практические последствия

1. Эксперимент верификатора: каждая модель-судья оценивает `orig` и `fail_pic`
   раздельно и вслепую по тексту, подписи и одной картинке.
2. Главный показатель: доля пар, где `F(orig) > F(fail_pic)`; дополнительно
   публикуются ничьи, обратные сравнения, средняя разность и результаты по типу
   искажения.
3. Эксперимент генерации: фронтирные генераторы получают тот же вход, что и
   собственный пайплайн, и сравниваются с ним по качеству результатов. Он не
   заменяет проверку способности судьи различать `orig` и `fail_pic`.
4. Если базовая модель не дообучалась авторами, вклад следует называть
   «верификатором/методом», а не «нашей VLM».
5. `gold` манифеста используется только после ответа судьи для оценки качества;
   его нельзя вставлять в запрос.
6. Краткие обоснования и сопоставления сущностей являются публичным аудитом.
   Внутренние рассуждения поставщика сохраняются только если реально переданы
   интерфейсом и не считаются обязательной частью результата.

## Гипотезы и непроверенные места

- **Гипотеза:** промпт по сущностям уменьшит число ничьих и повысит долю
  правильных пар по сравнению с общим промптом.
- **Гипотеза:** результаты будут сохраняться у моделей-судей разных семейств.
- Начальная модель-судья — `z-ai/glm-4.6v`; устойчивость выводов на других
  моделях ещё не проверена.
- Пороги достоверности `0.60/0.80` и веса общего балла являются начальными и
  требуют анализа чувствительности.
