# Выводы TASK_000 — Создание универсальной системы документации

[← К описанию](./000_descr.md) · [Журнал](./000_logs.md)

## Краткий итог

Создана универсальная переносимая система документации для программных,
исследовательских и связанных с данными проектов. Документация стала общей
постоянной памятью задач и исследований, а центральные страницы собираются из
локальных источников автоматически.

## Подтверждённые результаты и доказательства

- **Подтверждено:** универсальные правила находятся в корневом
  [`AGENTS.md`](../../../AGENTS.md).
- **Подтверждено:** полный порядок обслуживания описан в
  [регламенте](../../DOCUMENTATION_SYSTEM.md).
- **Подтверждено:** дерево навигации начинается с
  [`docs/index.md`](../../index.md).
- **Подтверждено:** все типы документов имеют
  [шаблоны](../../templates/index.md).
- **Подтверждено:** `scripts/docs_ctl.py` создаёт задачи, собирает общие страницы,
  блокирует конкурентную запись и проверяет связность.
- **Подтверждено:** команда `export-template` создаёт чистую основу нового
  проекта, исключая накопленные предметные задачи и знания.
- **Подтверждено:** два одновременно запущенных создания задач на чистой основе
  получили уникальные номера `TASK_001` и `TASK_002`, после чего проверка прошла
  без ошибок.
- **Подтверждено:** прежняя предметная информация сохранена в каталоге
  `_legacy_project_context/`, но исключена из универсальной рабочей документации
  и из экспортируемой основы.

## Полезные наблюдения

- Общую память обеспечивают файлы, а не субагенты и не история чата.
- Локальные файлы задач должны быть источниками истины; дашборд и текущее
  состояние безопаснее пересобирать автоматически.
- Исследовательская задача создаёт два результата: подробные выводы задачи и
  актуальную глобальную тематическую страницу.
- Стабильное описание проекта необходимо отделять от динамического состояния.
- Журнал должен хранить значимые события, а не копию терминала.
- Для научных и программных проектов необходимо различать подтверждённый факт,
  гипотезу, предложение, решение и устаревшее утверждение.

## Проблемы и преграды

- Старые рабочие файлы содержали проектно-зависимую информацию.
- Ручное редактирование общих страниц создавало риск гонок между чатами.
- Одна из крупных операций применения изменений не поддерживала удаление и
  повторное добавление одного файла в одном наборе изменений.
- В рабочей папке отсутствовал каталог `.git`, поэтому проверка через Git была
  недоступна.
- Параллельный чат создал предметную задачу и временно заменил служебную программу
  упрощённой версией без защиты от гонок.

## Как решались проблемы

- Старые материалы перемещены в отдельный архив без удаления.
- Центральные блоки сделаны автоматически собираемыми под файловой блокировкой.
- Изменение файлов разбито на безопасные последовательные операции.
- Проверка выполнена непосредственным чтением файлов, запуском служебной программы
  и обходом дерева ссылок.
- Параллельная задача сохранена; программа восстановлена после повторного чтения
  файлов и теперь собирает состояние обеих задач.
- Для повторного использования добавлен экспорт разрешённого набора универсальных
  файлов в новый каталог с последующей автоматической проверкой.

## Открытые вопросы

- Для нового проекта необходимо заполнить `MAIN_DESCRIPTION.md` первой предметной
  задачей.
- При росте до сотен страниц может потребоваться отдельный полнотекстовый поиск;
  текущая система намеренно использует только дерево ссылок и локальную проверку.
